# GOAL — 运维与变更智能体框架（项目章程）

> 2026-11-20 用户令重述刷入，全席位对齐基准；本文件为目标的唯一权威表述，各计划文档（`doc/plans/`）向此对齐。

## 0. 一句话定位

**构建一个运维和变更场景专用的智能体框架**：以**确定性方案**为核心资产、**动态方案**为兜底，以**历史案例的评审发布**为进化回路。

## 1. 场景域（两大面）

### 1.1 变更全流程
- **方案代码化生成**：变更方案以代码（langgraph 形式）表述并生成；
- **变更风控**；
- **变更前 / 中 / 后检测**与**回退**。

### 1.2 运维场景
- **告警配置**；
- **智能检测算法配置**；
- **诊断方案**：以识别**根因**；
- **快恢方案**：根据根因恢复系统。

## 2. ★ 核心闭环：基于历史案例的评审发布（本项目命脉，重点）

1. **案例收集**：由 **evolution service** 收集案例，作为**基线**；
2. **方案优化**：**opencode 在案例上优化确定性方案**——方案以 **langgraph 形式**表述；
3. **双门绿灯**（两门全过才放行）。**「全案例绿灯」是期望**；实际以**四大指标**牵引优化方向——**诊断/执行准确率、路由准确率、耗时、tokens 开销**，口径同 evolution service、无冲突：
   - 门一（质量）：**诊断/执行准确率、路由准确率**达标（期望=全案例绿灯）；
   - 门二（成本）：**耗时、tokens 开销优于原方案**（由 evolution service 评估）；
4. **基线化发布**：双门全过 → 确定性方案基线化发布。

## 3. 运行态双引擎策略

- **优先匹配确定性方案执行**——确保**能力的一致性**；确定性方案期望做到**无人值守**；
- **dynamic 方案兜底**——做到**自动化、人工看守**。

运行态入口与执行位置（2026-11-23 用户定夺）：在**同一网关**下，先由 **opencode 选 skill、提取参数**；skill 为 **langgraph 形式**时**绕过网关直接启动 langgraph 执行**——确定性方案的执行位置是**本仓**。
