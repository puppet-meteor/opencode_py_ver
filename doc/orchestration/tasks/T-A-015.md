【四项分叉】

分叉1【主脑→引擎的工具形态】
- (a) `src/opencode/tools/` 注册原生工具 workflow.run，仅主脑 agent 挂载（工人 agent 不挂）
- (b) 文档现方案（§11）：独立 workflow-mcp stdio 薄壳（MCP server），主脑经 MCP client 调用
- 约束：本仓形态 = 引擎与主脑同进程（sdk 进程内驱动）；MCP 壳原为"网关独立进程"形态设计；本仓 mcp/ 是 OC 作为 MCP client 的加载通道（OP-R4-1 自研最小客户端定案在案）。
- 待裁：v1 取哪个？工具挂载面如何隔离（防工人经同一工具再发起 workflow 形成工具级递归）？

分叉2【工人会话隔离模型】
- (a) 同一 opencode 服务进程内多会话（每工人一会话，靠 session 工作目录/权限规则隔离）
- (b) 每工人独立 `opencode run` 子进程（干完即回收）
- (c) 在所选之上再叠加 worktree-per-job（取消 = 整体丢弃，合并 = 验收）
- 约束：已知坑 = 服务 worker CWD 锁目录（在册）；工人须前摄权限边界（brief 白名单事后验收不够）；编码类任务需要 git 干净基线与可丢弃性。
- 待裁：v1 取哪种组合？前摄边界用什么机制承载（permission rules？agent 受限挂载？）？

分叉3【持久化双写边界】
- 现状：本仓已有 alembic 管理的关系存储（R1-S2 起）+ EventLog（R1-S6 起，事件事实源）；LangGraph checkpointer 自带 SQLite。
- 待裁：job 注册表（状态/参数/结果）进本仓存储还是 checkpointer？恢复顺序谁先？谁是 job 状态的"唯一事实源"？两者一致性如何保证（同事务 or 补偿）？

分叉4【直连路径调用包络与参数判定】

- 待裁：①"明确指定"的判定口径（slash/前端按钮/精确名引用算不算自然语言点名？"参数不全视同未显式落回主脑"由谁判定——网关按 schema 机器判，还是必须由前端表单保证）②直连包络字段（skill_id / params / conversation_anchor 的取舍）③直连 job 是否必须挂靠会话上下文（结果回写哪、主脑后续如何"知情"）。
