## 2. 契约基准（CORE-CONTRACTS §6.4 现读——W2 消费面）

- **裁定②（显式 reload capability；L340 翻面承接）**：快照刷新唯一路径=**宿主显式 reload 命令**。命令产生新快照：走 §6.1 版本路径（后续可执行快照使用新的 schema_version 并显式提供运行字段，保留版本 1 的解码与旧 fixture）+§6.2 canonical hash 重验（合法内容按重新规范化后的字节计算摘要，不能沿用旧摘要；提交与读取时重新验证，输入不符为 ValidationError）；旧快照含义不被静默改写——已存 `py.session.created` 及其 snapshot_hash 原样保留（§3.2 不删除日志前缀），新快照仅对显式 reload 之后的运行生效。L340 语义不变：**本能力是显式 capability 非静默热重载——文件事件本身永不触发快照改写或权限变化**，watcher 只提供提示与 idle 门槛下的显式 reload 机会，采纳与否归宿主定夺。
- **裁定③（idle 判定口径；语义归契约，阈值归实现切片）**：idle=三条件合取——①无在飞 run（reload 目标 session 无 accepted/running/cancelling 状态的 run——§2.1 状态域+§7 active-run 占用口径）；②无在飞审批（无 pending 的 `py.permission.requested`——§5.2 审批域，未回复未关闭未过期）；③静默窗（自①②最后清除时刻起经过实现切片定的静默窗口，且窗口内无新文件变更与命令活动——watcher 去重/合并纪律在 reload 门槛上的延伸）。idle 判定是**只读观察**，不取消/中断任何在飞活动；显式 reload 在应用点按 **§3.2 提交锁纪律原子复核** idle 前置，不满足即拒绝/顺延，绝不施于在飞 run/审批之上。静默窗与去重窗口具体阈值=契约待定面，实现切片定。
- **裁定④（boot_id/saved decision 跨快照衔接）**：boot_id 语义不变——每次应用启动生成（§5.2 既有句），显式 reload **不是**启动，不产生新 boot_id。旧快照下已记录的 saved 决定（`py.permission.saved`）跨快照边界与 §5.2 恢复边界同形：**保留作审计（durable 日志 append-only），不自动激活于新快照 regime**；新快照下的规则求值以该快照承载的 permission rules 为准，宿主新的 always 回复产生新决定（§5.2 既有机制沿用）。reload 本身**不写任何权限事件、不撤销/不激活任何 saved 决定**；旧 saved 决定在新快照 regime 下失效/存续的具体承载（到期、撤销事件或求值时门禁）归实现切片在「保留审计+不自动激活+审批面零触碰」语义内定。
- **红线段（§6.4 W2 承载条目）**：
  1. 「不改变运行中审批」（L65）：reload 全路径不得改变运行中审批——pending 审批的请求/回复/关闭路径与运行中权限求值在 reload 前后保持不变。
  2. 「不静默改写旧快照含义」（§6.1/§6.2 沿用）：旧快照事实与新快照按版本路径并存，canonical hash 重验，旧 fixture 保持可读。
  3. watch 任务生命周期：取消/close 必须回收 watch 任务（§7 不遗留后台任务纪律）。
- **fixture 行为要求（§6.4 L417，W2 份额）**：idle 门槛拒绝/顺延分支、显式 reload→新快照 §6.2 hash 重验往返、saved 决定跨快照保留审计不自动激活——均须以正/反例 fixture 锁定形状与行为。
