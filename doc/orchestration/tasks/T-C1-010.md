【契约基准】（行号级，`doc/CORE-CONTRACTS.md`）
1. §7 L298-312 方法表——**R1 子集 = create/session_status/messages/run_status/prompt/close**；`cancel`/`reply_permission`/`revoke_permission` **不实现**（L325"R1 不实现下述运行 cancel/恢复协调器"；不写占位 stub）。session_status 不触发恢复或外部调用；messages 游标必须属于该 session；close 按序取消并收回自有任务、不得遗留后台任务。
2. §7 L314 返参形状：`SessionRef={session_id}`；`RunRef={session_id, run_id, request_id}` 三项均非空字符串，session_id/run_id 另须满足 §3.1 ses_/run_ pattern，request_id 由调用方给定、仅非空字符串**不强制前缀**；`RunStatus` 含上述标识及 `status: accepted/running/cancelling/succeeded/failed/interrupted`、可选 error（R1 只有 accepted 可达）；MessagePage 含 items/next_message_id/has_more（S6 storage/repos.py 已有，直接复用）。
3. §7 L316：R1 的 prompt 只提交一个 `py.prompt.accepted(version=1)`，data 中 request_id/run_id 与返回 RunRef 一致，message 为本次 text 创建的 UserMessage（contracts §2.1 模型），metadata 含同一 run_id/request_id；其 projector 同事务插入一条 UserMessage、**置 active_run_id** 并得到 accepted 的 RunStatus；只有事务提交成功才返回；不产生 run.started、assistant/idle 或调度任务，不调用 provider/工具。
4. §7 L318-323 四步固定顺序（**顺序即语义**）：
   - **步1 状态门禁**（含入参校验）：session_id/request_id 是非空字符串、session_id 符合 §3.1 ses_ pattern、text 是字符串（不隐式转换）；session 不存在→NotFound；read_only_diagnostic→**始终** SessionReadOnly，**包括同 request_id 的重试**（门禁先于幂等查询——§3.2.1"S7 以 SessionReadOnly 拒绝（先于幂等查询）"；r1-slices L144 括注"除非命中第 2 步幂等"与契约冲突，**以契约为准作废**）；cleanup_failed/closed→LifecycleCleanupFailed/SessionClosed；session 为 active 后再检查 service 的 closing/closed gate，关闭中或已关闭→SessionClosed。
   - **步2 durable 幂等查询**（先于步3/4）：以 `(session_id, dedupe_key)` 查原接受记录，key 精确为 `"prompt:" + request_id`（字符串拼接、大小写敏感、跨 session 可复用、受 §3.2 唯一约束保护）；命中→原 message.text 与本次 text 逐 Unicode code point 比较：相同→直接返回原 RunRef（不生成新 message/run/event/batch ID、不重投影、不重发通知；不 trim、不归一化换行/Unicode；run 已终结时也返回首次 RunRef）；不同→IdempotencyConflict（即使当前 busy；比较不使用新生成的 ID/时间，也不只依赖摘要）。原文本从存储的 `PromptAcceptedData.message.text` 取（contracts/events.py L114-121）。
   - **步3 active_run_id 门禁**：已占→SessionBusy。
   - **步4** 通过后才生成并固定 message/run/event/batch ID 与时间（evt_/msg_/run_ 均须 §3.1 pattern）、按 §3.2 读取 H 作为 expected_seq 并走 `SessionStore.commit`；完全相同的提交重试复用这些值；提交失败/回滚不留下 request_id、消息或 active run。不同 request_id 的并发 prompt 最多一个成功（跨进程由 expected_seq 乐观并发兜底——S3 已测）；相同请求并发成功后都指向同一个 RunRef。
5. §7 L325 R1 accepted 占槽：跨 close/reopen 持续占用 active-run 槽（无终态、不自动释放）；R1 close 只释放其 storage/Bus 等自有资源，不为 accepted 追加取消/终态；关闭并重开后保持 accepted——新 request_id 仍返回 SessionBusy，同一请求仍按上述规则幂等返回。
6. §6.1 L283 config_snapshot：R1 字段全集精确为 `{"schema_version":1,"permission_rules":[]}`（两字段都必须显式存在、版本必须是整数 1、permission_rules 必须为空；拒额外键/null/字符串布尔浮点版本号/非空规则）；§6.2 canonical JSON+SHA-256——**复用 contracts 的 `ConfigSnapshot` 模型与 `compute_snapshot_hash`，勿重造**；固定摘要见 L290。
7. §3.1 L114 四前缀强制（模型层已有，T-C1-002 落实）；L122 py.session.created data=working_dir/config_snapshot/snapshot_hash。
