**1. service.prompt 调度**（§7 L331）：
- accepted 提交成功后**创建并调度 runner 任务**（asyncio 任务**强引用**——§7 L331 末句）；只调度本次新接受的请求；

**2. cancel(run_id)**（§7 L335 全分支逐句落）：
- dedupe_key=`cancel:run_id`；**重复 cancel 等待同一清理任务**（不重复提交）；
- 已结束 → 返回原 RunStatus（**run.finished 先提交则迟到 cancel 不覆盖**）；
- 未结束 → 提交取消意图 + 关闭待审批/未开始调用 → cancelling；已开始工具**如实保存已确定结果不伪装"未执行"**；
- 取消意图先提交 → 不再启动新 step/tool、清理后 interrupted（§2.1 L59-61 链路——runner 消费面已落地）；
- 迟到完成回调按 execution_id 去重；
- 清理无法确认 → **LifecycleCleanupFailed** 且 session 不可再执行。

**3. run_status(run_id)**（§3.2 L187——OP-2 已裁 T-A-005）：经 runs 读模型按 run_id 查表解析归属和状态；**正常查询不扫描全量 events**；所需投影缺失、归属或状态损坏按 §3.2.1 返回 StorageCorrupt，不臆造 RunStatus。

**4. close() R2 生命周期**（§7 L337 全序逐句落）：
首次调用原子进 closing gate（拒新 prompt/工具调度/权限写入）→ 每个可写 session 活动 run 提交 `py.run.cancel_requested(reason=shutdown)` →（R2 无 pending approval，permission.closed 分支不可达——**OP-9 浮报清单必列**）→ 释放提交锁 → 等待 provider stream/adapter → 期间仍可经同一 SessionStore.commit 写已确定 tool/step/run 终态 → 关闭超时外部结果仍不确定：可写则 `tool.finished(effect_status=unknown)`+interrupted step/run 终态+session cleanup_failed、不可写则保留记录不报告已清理 → 全部自有任务退出或 durable 标记后关 provider/DB → service closed；并发/重复 close 复用同一清理任务不重复提交。

- run.started 先提交 → running 进 cancelling（取消意图作用于运行中 run）。
