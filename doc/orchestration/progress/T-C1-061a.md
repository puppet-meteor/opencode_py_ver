## ① 诊断记录

### 四范围现读

**1. src 清扫机制（现读；定谳四问逐答）**
- 清扫 API：Windows = JobObject（`src/opencode/process/winjob.py`，stdlib-ctypes）：`CreateJobObjectW` + `SetInformationJobObject(JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE=0x2000)`；spawn 时捕获（`StdioTransport.start`，`self._job = self._capture_in_job()`，stdio.py ~L175）；扫树 = `TerminateJobObject(job, 1)`（`_terminate_tree` stdio.py L507-527 与 `_kill_tree_hard` L528-540，两级同用 exit code 1）；`JOB_OBJECT_LIMIT_BREAKAWAY_OK` 故意不设（winjob docstring：成员资格创建时继承，无 taskkill 式枚举快照竞态）。POSIX = `start_new_session` + `os.killpg`（本 face 非 CI 红面）。
- 清扫时序：crash 路径清扫**不是 fire-and-forget**。链：`_read_stdout` EOF → `_stdout_ended`（stdio.py L349-380：stderr 有限等待 ≤1s + `proc.wait()` ≤1s）→ `on_unexpected_exit`（= `_mark_lost`，manager.py L301，同步记账，不起任务）→ `_fail_pending`（call_tool 在此解锁抛错）→ **`await self.close()` 就在 reader task 内 inline await**（L371）→ crash 分支（`returncode=3≠None`，L219-231）→ `_terminate_tree()` + `_kill_tree_hard()` 同步内核调用 → `_job.close()` KILL_ON_JOB_CLOSE 兜底（L243-246）。模块内仅有的 create_task = 两条 pipe reader（L178-179）。清扫前一切等待有界 ≤2s。
- child 枚举来源：无枚举（成员资格创建时继承）——CORE-CONTRACTS §5.3 首名形态，设计上无快照竞态。
- 清扫失败有无重试/上报：**皆无**。三层静默退化：① `_capture_in_job` L494-504 捕 OSError → `return None`（先 `job.close()` 再 None），零日志零上报；② `_terminate_tree`/`_kill_tree_hard` 的 `except OSError: pass` → 落到仅主进程杀；③ close() 末尾的 KILL_ON_JOB_CLOSE 兜底在 `_job is None` 时不存在。

**2. fixture 面（现读，零触碰）**
`crash_with_child`（`tests/integration/mcp_stdio_server.py`）：`_spawn_child()` = `subprocess.Popen([sys.executable, "-c", "import time; time.sleep(120)"], stdin/stdout/stderr=DEVNULL)`——普通 child，无 detached/新进程组/breakaway 旗标 ⇒ capture 成功时必然继承 job 成员；child 不持任何管道句柄（DEVNULL），不影响 EOF 传播；时序为 initialize 后先 spawn child、首个 tools/call 才 exit(3)。⇒ **fixture 与契约形态一致**：只要 capture 成功，清扫必覆盖 child——现读未发现 fixture 侧缺陷。

**3. 探针面（现读，未改——(c) 证伪故写权限①前置不成立）**
`_pid_alive`（test_mcp_stdio.py L76-108）：win32 = OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION) → `GetExitCodeProcess == STILL_ACTIVE(259)`。259 碰撞窗口理论上存在（恰以 259 退出的进程永久误报活），但本测试所有路径**无 259 生产者**：两级 job 终止用 exit code 1；server 自愿退出 3；child 自然退出 0（且在 120s，窗外）。探针自身失败方向是**假死**（OpenProcess/GetExitCodeProcess 失败 → False，即「真泄漏漏报」），非假活。POSIX 分支 os.kill(pid,0) 语义差——本 CI 红仅 windows，非判据面。

**4. CI 证据面（现读）**
两现均为「轮询窗到点仍存活」（CI-179 旧 L119 `[4192]`，10s 窗；CI-181 新 L125 `[3632]`，30s 窗）——窗宽 10→30 只改了红的迟到时间，未改变「存活」事实本身；两现 raises 侧 `match="exited with code 3"` 均通过 ⇒ 诊断链完成 ⇒ reader 到达 `_fail_pending` ⇒ `await self.close()` 必在 EOF 后 ≤~2s 内开始执行清扫。姊妹测试 `test_close_escalation_kills_tree`（同样依赖 job 清扫、文件序相邻）两现均绿；ubuntu 两现均绿；attempt-2 rerun 绿；本地面零再现。

### 三假说证实/证伪
- **(b) 清扫排队慢——证伪**：crash 清扫是 reader task 内 inline await；清扫前等待全部有界 ≤2s；测试的 `_wait_pids_gone` 每轮 sleep 0.05s 让出事件循环 ⇒ 同一 loop 调度语义下不存在 >30s 清扫延迟的构造方式。
- **(c) 探针假阳——证伪**：无 259 退出码生产者（清扫用 1；自然退出 3/0）；pid 复用需 PID 计数器回绕（百万级分配量，584s run 内不可达，且须恰好落进单个 50ms tick 间隙）；探针失败方向为假死。「整窗 30s 假活」无机制。
- **(a) 清扫 miss——证实（机制收窄）**：幸存 pid 必为 child（票面推定复核成立：server 自愿退出 3 ⇒ GetExitCodeProcess=3≠259 ⇒ 探针立报死，唯一可能幸存者=child）。child 在清扫列表之外，而「列表为空」唯一可能形态 = `_capture_in_job` spawn 时返回 None（进入静默 fallback）⇒ 两级树杀退化为仅主进程 ⇒ server 已死，terminate/kill 皆 no-op ⇒ child 活满 120s ⇒ 窗到点红。反向情形（job 存在且含 child 而 TerminateJobObject 杀不掉）需内核级故障且 attempt-2 同镜像通过，矛盾，排除。

### 根因定谳链
CI-179/CI-181 两现 + attempt-2 绿 + 本地零再现 ⇒ 间歇性、spawn 时刻、runner 环境依赖的 job capture 失败；触发器候选：对新鲜未签名 python 进程的 WDAC/AV 类瞬时 ACCESS_DENIED（OpenProcess/AssignProcessToJobObject 面——本仓库 #167 已有同 runner 镜像 WDAC 间歇先例）、或负载下 CreateJobObjectW/句柄压力类资源失败。**精确触发器从现有日志不可证——fallback 本身静默（零日志/零重试/零暴露面），两现红均不携带任何 capture 侧证据。该静默性本身即缺陷第一项。**

## ② 处置：停下上浮（src 侧；触发票面「停下上浮条款」）

1. **fallback 可观测化**：`_capture_in_job` 在 `return None` 及 `return job`（exited 空壳）两形都应记日志并暴露（如 transport 属性 `job_capture_error`）——否则未来任何 CI 红都不可归因（本票 triage 成本即其直接后果）。
2. **有界重试**：对 OpenProcess/AssignProcessToJobObject 的 OSError 做短重试（如 3 次、50-100ms 退避）——WDAC/AV 类瞬时拒绝恰是有界重试可吸收的类别；治本形态为 CREATE_SUSPENDED + assign + resume（spawn 零竞态，但需绕开 asyncio create_subprocess_exec 的自建 spawn 路径，变更面大，供权衡）。
3. **最坏情形上报**：capture 终究失败时 close() 面应仍有可观测信号（今日清扫静默 no-op，KILL_ON_JOB_CLOSE 兜底不存在）。
4. 配套测试建议（本票未做，断言面冻结）：连接成功后 assert capture 结果（`job_captured` 面），使 runner 瞬时 capture 失败以「capture 失败」即时显性红，而非模糊的幸存者红。
