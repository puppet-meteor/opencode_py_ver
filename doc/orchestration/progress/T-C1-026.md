## ① 方案审视发现（选型论证）

- **policy 单文件选型**：`src/opencode/tools/policy.py` 单文件承载引擎+协调器（PermissionPolicy 语义面 + ApprovalCoordinator 通道面），imports 仅契约层（contracts-only），不 import service/session——环不存在；`service.py` 仅在 TYPE_CHECKING 下引 policy 类型，运行期无新依赖边。`contracts/permissions.py` 未创建：PermissionDecision/DecisionReceipt 是运行期/服务面形状而非 wire 契约（六型 S1 事件已够），落位 policy.py+service.py。
- **审批通道架构（invoker 等待与 service 回复协作）**：Coordinator 持 pending 表（permission_id → PermissionRequest+future）+ 每审批一个 asyncio 到期 watchdog；`register` 幂等拒绝重复（fail-closed），`close_run`/`close_all` 决出 cancelled（reason 区分 run 取消/服务关闭），`resolve_reply` 以 `ReplyResolution(status: replied|late|unknown, outcome)` 返回——**跨 await 边界不抛异常**，错误分类映射留给 service 面（unknown→NotFound、late+expired→ApprovalExpired、late+other→Conflict），§7 L173 首个合法迁移胜由 coordinator 单 CAS 点执法。
- **挂点控制流**：`invoke_tool(policy=...)` → `_apply_policy` 返回 `ToolOutcome | Literal["started", "proceed"]`：ToolOutcome=终态（策略 deny/通道未连/到期/取消）；`"started"`=ask 批准路径已提交 `[replied (, saved), started]` 同批（调用方直入 adapter 执行）；`"proceed"`=纯 allow，调用方自提交 started（携带 permission_decision="allow"）。`policy=None` 保持 R2 默认 allow 面不变——`R2_PERMISSION_DECISION` 占位拆除、真值上 wire（§5.2 L264 语义在无策略面原样）。
- **决策评估序**：宿主硬性 deny → 根目录限制（仅 fs__ 族，根外/不可解析=deny fail-closed）→ saved 决定（精确 (session_id, action, resources)+当前 boot）→ 规则（host 先于 project、首配胜）→ 默认表（fs__read/glob/grep/ls=allow、fs__write/fs__edit=ask、bash/mcp 命名空间=ask、其余按声明 side_effects 兜底）。
- **always 的 replied+saved 事件序**：同批 `[replied, saved, started]`（裁定④-2 成对纪律外延到决定三型）；saved 载具体 action/resource 规则+session+boot 作用域（无范围通配拒绝）；内存决定注册后置于 durable 提交之后（fail-closed 方向）。`once` 仅当次 permission_id 生效；unknown 效果同 (session_id, action, input_hash) 重试进 `_unknown_retries` 阻断复用（§5.2 L270）。
- **到期任务实现形态**：register 时创建 per-approval watchdog task，决出 `expired`；Invoker 以 closed-first 同批提交 `[closed(expired), finished(cancelled/not_started + ApprovalUnavailable)]`；默认 300 秒经 App 装配（`DEFAULT_APPROVAL_TIMEOUT_S`），`App(approval_timeout_s=...)` 为测试缝。
- **boot_id 铸造与消费（裁定④-3）**：App 构造时铸 `boot_{uuid4().hex}`，经 policy 注入；只激活当前 boot 的 saved 决定，异 boot 行保留审计不激活（revoke 对其 NotFound）；新 always 产生新决定。
- **cancel/close 序（实现中修正，推翻早稿）**：原序 close_run/close_all 先于取消意图——唤醒 parked Invoker 的提交风暴对 service 意图重试形成 ConflictError 耗尽（真实调度器暴露的真实失败）。修正序：**同步置协作取消信号 → 静默下提交 durable 取消意图 → close_run/close_all 决出 pending**。fold 合法性：CANCELLING 对 permission.closed 非终态；Invoker allow 后复核取消信号覆盖残窗（allow-vs-cancel 竞态折 cancelled 对，回复留内存——R2 分支 2 语义合法折）。cancel()/close() 排干任务后才返回。
- **服务面**：`reply_permission` 校验（词表 §3.1 L136/非空 id/通道在位）→ 诊断门（pending request 的 session，拒于 CAS 前）→ coordinator CAS → DecisionReceipt（§7 L322：ack 非可复用令牌）；`revoke_permission` 诊断门+state 门+会话锁下 bounded Conflict 重试提交 revoked。
- **mypy 边界钉定三处**（类型面不变量）：reply 词表 cast、allow 仅自宿主回复（`outcome.reply` 非 None 断言）、catalog-miss 早退后 `tool_ref` 钉定。
- **OP-R3-5 保守读法**：只保证档位可配置面（规则集+默认表数据驱动可注入），默认保守 ask（write/edit/bash/MCP），未预写裁决。

## ③ 强制浮报清单（四档）

**协议不可达（结构性）**：
- 真实进程重启不可达：boot_id 重启=同进程第二 App over 同数据目录（app1 全关后 app2 `mode="readwrite"`），非真进程重启——内存注册表空置等价成立。
- 300 秒真实到期不可达：默认值以契约测试钉（coordinator 校验+默认 deadline）；端到端到期以 `approval_timeout_s=0.05` 短真实超时驱动（真实时钟非注入时钟），300s 全程等待不可测。
- upcaster 旧版本路径不可达：首版 v1 注册无 v2 存量（r3-slices §3 台账 #24 前瞻，非本切片工作）。

**未测防御**：
- coordinator `register` 于 close_all 后的 RuntimeError 拒绝：纯防御断言于契约层，无端到端路径。
- 无 provider 的 App 级 ask 路径：App 无 provider→无 run→invoke 不可达（结构上；R1 面零行为变更由 703 基线覆盖）。
- fs__ 根限制的符号链接逃逸深例：以 unresolvable+monkeypatch Path 钉 fail-closed 方向，未逐符号链接拓扑。
- `_unknown_retries` 的跨进程持久性：块表在内存，重启即清（与 saved 激活面同 boot 语义一致，非缺陷但未断言）。

- 竞态**真实调度器**（无注入时钟、无注入 committer）：cancel/close 竞态两分支（cancelled 对 vs interrupted fold）、allow-vs-cancel 残窗复核、pre-registration 回复窗（见注记）——cancel/close 序修正是真实失败驱动（ConflictError 风暴复现→修→绿）。
