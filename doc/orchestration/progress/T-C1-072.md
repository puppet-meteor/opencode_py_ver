## S1 backend decision (decided BEFORE any tool implementation — L68: verification precedes wiring)

**Decision: option (a) — the pywinpty legacy winpty agent backend (`winpty.enums.Backend.WinPTY`) carries the T1 Windows tool.**

Rationale (from the T0 evidence three faces, fresh reads this session):

- `doc/evidence/pty0/platform.json` ctrl_c backend_observations: the legacy winpty agent delivers PTY-written `\x03` (child KeyboardInterrupt marker + exit code 130, `backend_used: "winpty (legacy agent)"`); the vendored ConPTY host does NOT dispatch the console control event within the observation window (child_exit_code null). ctrl_c — the cancellation primitive every tool call depends on — is verified ONLY on the winpty agent backend.
- Option (b) (ConPTY + self-layered control-event mechanism) would require inventing a Win32 mechanism with NO T0 support and a recorded negative result (vendored ConPTY does not dispatch PTY-written 0x03); no pywinpty API exposes console attachment for an out-of-process pseudoconsole host. That is unverified research, the opposite of the minimal-risk path the evidence supports.
- Option (a) requires supplementary verification of exactly three primitives (resize/encoding/process_tree_exit) on the winpty agent backend — all reachable through the same mature `PtyProcess` API surface (`setwinsize`/`write`/`read`/`pid`/`exitstatus`) T0 already exercised on that backend's ctrl_c leg.
- p2-slices L169's "ConPTY" wording is superseded by the S1 empirical ruling per the ticket's own instruction (L68 semantics: verification precedes wiring — the backend that actually carries all four primitives is the one that carries the tool).

Supplementary verification of the remaining three primitives on this backend happens BEFORE tool implementation, as real test assertions in `tests/integration/test_pty_s1_winpty_backend.py`, with per-primitive entries recorded below.
