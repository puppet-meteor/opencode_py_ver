## ① 方案审视发现（选型论证）

- **e2e 组合选型**：FakeOpenAIServer 在 async 测试自身事件循环内 `await start()`/`await aclose()`（无需 test_cli.py 的线程宿主形态——该形态服务于子进程 CLI）；组合 `App(db_path, working_dir=str(tmp_path), provider=MaasAdapter(f"{base_url}/v1", key), tools=(FsReadAdapter(),), settings=RuntimeSettings(model=ModelRef(provider="maas", model="fake-model"), context_limit=100_000, output_reserve=4096, timeout_s=30.0))`；alembic 真 CLI 建库（`_upgrade_head` 同形态重建自 test_messages_union.py）。真实全栈：真 HTTP→SSE 解析→ContextBuilder→runner→Invoker→`fs__read` 真实文件系统读→SQLite 投影。
- **"多轮文本"两读并防**：会话轮读法=3 轮各自独立 prompt→独立 run.finished；多段流读法=第 2 轮脚本 2 段 delta（"seg one "+"seg two"）→finalized 单 part，全文逐字断言（"seg one seg two"）。
- **中断注入选型**：`ScriptedResponse(frames=[Frame(text_delta_frame("partial tex"))], omit_done=True)`——干净 body 结束但无 SSE [DONE] 终止行（EOF-without-terminal）。比 500 状态更贴"生成流中途断"（部分 delta 已落、终态前断流），比 `hang_after_frames` 确定性高（无需超时等待）。
- **计数选型**：EventLog SQL（`SELECT type FROM events WHERE session_id=? ORDER BY seq` 后计数）——durable、可审计；另以 `server.requests` 数量做 provider 侧交叉验证；终态查询一律走 `run_status` 读模型（OP-2，不扫描 events）。
- **证据文档核验方法**：r1-exit-evidence 模式照搬 + PHASE1-SLIM L76-85 逐行原文核验 + `doc/reviews/` 实际文件名（`Get-ChildItem` 枚举）+ ORCHESTRATION 台账锚点（仅引任务书/checkpoint 已载数字，未逐切片复核）。
