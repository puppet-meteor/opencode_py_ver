## ① 方案审视发现

- **close 只取消"活调度"读法**（§7 L337 与 L331 R1 规则的调和）：close 仅对 `self._tasks` 中在册的 LIVE 调度任务提交 shutdown intent；storage-only accepted run（无活任务：引擎未接或跨进程遗留）保留记录交 R4 恢复协调器，从不谎称已清理。由 `test_close_keeps_storage_only_accepted_runs_for_recovery` 钉定。
- **close 超时走 (a) 读法**：超时 pending 的每个任务先硬 `task.cancel()` + 宽限等待（`_CLOSE_GRACE_S=1.0`），让 runner 的 CancelledError 处理器在 session 仍可写时提交 `tool.finished(unknown/unknown)` + interrupted 终态；宽限后仍卡死的任务放弃（记录保留，③浮报）→ 对应 session 标记 `cleanup_failed`，重开走 LifecycleCleanupFailed。
- **cancel 语义落法**：终态 run 原样返回 RunStatus（晚到 cancel 绝不覆盖已提交结果）；非终态：session 锁内 check-first 去重（`cancel:run_id` dedupe key，重复 cancel 永不再提交）+ **ConflictError 重试循环内重读终态**（无此重查，intent 可能落在终态 run 上——fold 会 IllegalTransition → StorageCorrupt）；锁外设协作信号后 await 同一任务；无活任务 → 返回 CANCELLING 交 R4 收终态；任务已崩（`_schedule_errors`）→ 标 cleanup_failed + 抛 LifecycleCleanupFailedError（链上原错误）。
- **协作信号不中断在途 provider 流**：cancel 不 abort mid-chunk 流（`_consume` 不看信号；`_run_tools` 每工具前查、step 边界查；硬 CancelledError 由 run() L450-458 处理）——由 mid-run cancel 测试钉定（收到的 text 保留、§8 L350 无重发）。
- **引擎缝（seam）**：冻结 `ReadRepositories` 无 runs 查询面、无 cleanup_failed 写面（T-C1-014 均未授权）→ service.py 持有注入 engine 上的单行 `sa.text` 查询 + 一条管理 UPDATE。④ 建议 repos 微补丁收编。
- **RunScheduler Protocol 置于 service.py**（runner.py 反向 import service，真协议放 runner 会循环引用）；app.py 传具体 Runner。provider close 面：冻结 Provider 协议无 close → app.py 自设 `_ProviderHandle` Protocol（stream + close）传 `provider.close`。
- **App 共享同一 ids 工厂 + 注入时钟**：service/EventCommitter/ToolRegistry/Runner 同一 AscendingIds（分开实例同毫秒可铸重复 id）。
- **prompt 调度对 close 气密**：`_schedule_run` 的 `_closing` 重查与 `create_task` 同一同步块（查与注册间无 await）；调度发生于 prompt 提交锁内 notify 之后；幂等重试路径永不调度（仅新 accepted）。
- **无引擎构造回退**：run_status 回退 R1 active-slot 路径（保 test_service.py L523-551 既有钉定）；cancel 无引擎面拒绝 StoreValidationError（回退面无法诚实报 cancelling）。
- **`RunStatusValue.is_terminal` 属性**：service.py 自有枚举缺该面（state.py RunStatus 有）→ 镜像 `_RUN_NON_TERMINAL` 模式补齐（cancel/close 终态判断需要）。
- **本席测试设计事故（重要教训，②详）**：corruption 变体最初以同步 `sqlite3` 直写 DB，与并发 runner 写事务竞态——被挂起的 runner 事务持 SQLite 锁、测试同步代码阻塞事件循环、持锁者永无机会提交 → aiosqlite future 永久挂起（协程链栈实证：parker 在 `_advance_applied_seq` UPDATE / `log_high` 读路径）。修法：**各变体先 await run 至终态再同步变异**（腐败面是读模型分类，本无需活任务）。非实现缺陷，已写入测试注释钉定该纪律。

## ③ 强制浮报清单

**协议不可达（2）**
1. **OP-9：close 的 permission.closed 分支在 R2 不可达**（R2 无 pending approval 环节），协议性未测，按任务书要求列此备案。
2. prompt 提交锁内 `_closing` 置位与 `_schedule_run` 注册同线程同步序（查与 create_task 间无 await）：close 要么见到在册任务要么令调度 no-op，竞窗本身在单线程事件循环内不可达。

**未测防御（4）**
1. **late-cancel vs run.finished 提交竞窗**（cancel 的 ConflictError 重试循环内终态重查防线）：重试循环内再读终态的时窗无法在不插 store 钩子的前提下注入（需要受控让 runner 在 cancel 读后/提交前抢插——store 面无此钩子）。防线代码在 `_commit_cancel_intent` 重查支。
2. **宽限后仍卡死的任务放弃路径**：需一个同时无视协作信号与 task.cancel() 的工具（现有 `_GatedAdapter` 忽略信号但可被硬取消；构造不可硬取消且 Python 级不可中断的 adapter 需屏蔽 CancelledError，违背测试纪律），故仅测到"超时→cancel→grace→cleanup_failed"为止，放弃支未测。
3. **双痕迹齐删的 NotFound 边界**（runs 行与 events 俱删 → run_status 应 NotFound 而非 corrupt）：本批变体覆盖单删（行删→corrupt / 从未存在→NotFound），双删边界未单独钉定。
4. **close 时 session 已被隔离（quarantine）且仍有活任务**：Phase 1 的 shutdown intent 提交会抛 SessionReadOnlyError 并穿出 close（本席实测发现：corruption 变体若留活任务即触发）。行为与 R1 close 语义一致（提交错误传播），但后果是 provider/engine 未关——是否应改为"容忍 + 该任务走 cleanup_failed"请调度器裁量（见 ④-4）。

**已测防御（本批 14 测钉定）**
调度+全事件序列+槽释放+idle 消息；幂等重试不调度不追加；cancelling 占 busy 槽；终态 cancel 原样返回；mid-run cancel 文本保留/无重发/无新工具；并发 cancel 单 intent 同终态；cancel-first 拒 run.started 且无该事件直接 interrupted；无引擎 cancel 拒绝；run_status 历史解析零 events 扫描；六变体 fail-closed 分类（含隔离位）；close 全序+provider 单关；并发/重复 close 复用单清理；超时 unknown 工具+cleanup_failed+重开 LifecycleCleanupFailed；storage-only accepted 保留。

**架构注记（4）**
1. service.py 直持 engine 上 runs 表单行查询 + cleanup_failed 管理 UPDATE——repos 未授权前的缝内落法（④-3 收编建议）。
2. `RunScheduler`/`_ProviderHandle` 双 Protocol 均为绕开冻结面（runner↔service 循环引用、Provider 无 close）的最小 seam。
3. App 组合根共享 ids 工厂/时钟（防同毫秒重复 id）；无 provider 时完整退化为 R1 行为（既有 test_service.py 全绿为证）。
4. 集成测试纪律（本席实证）：**同步 sqlite 直写不得与活 runner 并发**（挂起写事务持锁 + 同步代码阻塞循环 = aiosqlite future 死锁），已写入 test L706-710 注释。
